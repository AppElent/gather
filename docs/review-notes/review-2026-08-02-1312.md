## Action Items

### Blockers

- [ ] **Deleting a task list does nothing, and fails silently either way**
  - **What:** On `/g/<slug>/tasks`, clicking the trash icon on a local list
    ("Test list") does not delete it. Nothing visible happens — no error, no
    toast, no console surface to the user. Traced end to end and the wiring is
    correct, so the failure is at one of two points, both of which are silent by
    construction: (a) `window.confirm` returns `false` because modals are
    suppressed in the embedded preview frame, or (b) the Convex mutation rejects
    in `requireListAccess` and the rejection is discarded. The observed cause was
    not isolated during the session, so **fix both** — the result is correct
    regardless of which one it was.
  - **Where:** `/g/<slug>/tasks` ->
    `src/components/tasks/LocalTaskList.tsx:68-76` (trash button,
    `onClick={onRemoveList}`) ->
    `src/components/tasks/TasksPage.tsx:32-36` (`confirmRemove`, the
    `window.confirm` + bare `void removeList(...)`) ->
    `convex/taskLists.ts:106-117` (`remove` mutation, `requireListAccess` then
    cascade delete). Same trash button exists on
    `src/components/tasks/ExternalTaskList.tsx` via the same `onRemoveList` prop.
  - **Type:** bug
  - **Fix direction:** Replace the `window.confirm` in `confirmRemove` with an
    in-app confirmation (a small confirm state on the card, or a dialog built
    from the existing `shell-*` primitives in
    `src/components/app/ShellPrimitives.tsx`) so deletion never depends on a
    native modal the frame can suppress. Then make the mutation's failure
    visible: `await` it inside an `async` handler with `try`/`catch`, hold the
    message in state, and render it where the page already renders errors. Apply
    the same treatment to the other four `window.confirm`-guarded destructive
    actions, which have the identical failure mode: `EditBabyPage.tsx:61`
    (delete baby), `Timeline.tsx:103` (delete entry), `FoodDetailPage.tsx:83`
    (delete food), `ConnectionsSettings.tsx:115` (disconnect integration).
  - **Acceptance:** On `/g/<slug>/tasks` with a local list present, clicking its
    trash icon shows an in-app confirmation; confirming removes the card from
    the grid and the list stays gone after a reload, with its tasks deleted too.
    Cancelling leaves the list untouched. If the mutation rejects, a readable
    error message appears on the page rather than nothing. No `window.confirm`
    remains in `src/` outside tests. Deleting a baby, a baby entry, a food, and
    disconnecting an integration each behave the same way.

### Major

- [ ] **Topbar hamburger renders on desktop, where clicking it does nothing**
  - **What:** The "Open navigation" hamburger in the sticky topbar is visible at
    desktop width, next to a sidebar that is already on screen. Clicking it has
    no visible effect. It is meant to be phone-only. Root cause is a CSS cascade
    bug with a blast radius well beyond this one button: `.shell-icon-button` is
    declared **unlayered** in `src/styles.css`, after `@import "tailwindcss"`.
    In Tailwind v4 every Tailwind rule lives in a cascade layer, and unlayered
    CSS beats any layered CSS regardless of specificity — so the `md:hidden`
    utility on the button loses to `.shell-icon-button { display: inline-grid }`
    and never applies. The drawer it opens is gated by `md:hidden` on its
    backdrop, which is plain Tailwind with nothing competing, so that half
    correctly stays hidden — hence a control that is visible but inert.
  - **Where:** `src/components/app/Topbar.tsx:23-29` (the `IconButton`, passing
    `className="md:hidden"`); `src/components/app/ShellPrimitives.tsx:21` (which
    does correctly append the incoming `className`);
    `src/styles.css:132` (`.shell-icon-button`, the unlayered rule that wins);
    `src/components/app/AppShell.tsx:121-150` (the drawer, backdrop gated
    `md:hidden` at line 124).
  - **Type:** bug
  - **Fix direction:** Fix the cascade, not just this button — wrap the app's own
    class rules in `src/styles.css` in `@layer components { … }` so Tailwind
    utilities can override them as intended. Roughly 50 unlayered rules are
    affected (`.app-shell`, `.shell-*`, `.demo-*`, `.rm-*`, `.page-wrap`,
    `.display-title`, `.island-*`, `.feature-card`, `.nav-link`, `.site-footer`,
    `.rise-in`), all carrying the same latent trap. Check the whole app for
    layout that silently depended on the broken precedence before committing.
    If a full re-layering looks too broad for this PR, the narrow alternative is
    to move `.shell-icon-button` alone into `@layer components` — but say so in
    the commit, because the rest of the trap stays armed.
  - **Acceptance:** At >=768px the hamburger is not in the DOM's rendered box
    (computed `display: none`); at <768px it is visible and opens the navigation
    drawer as before. No other page's layout changes as a side effect of the
    re-layering. `pnpm build` passes and the five gates stay green.

- [ ] **Navigating to Groups drops the Group you were in**
  - **What:** Following the sidebar's "Groups" link empties the shell: the
    sidebar's module list is replaced by "Pick a group to see its modules.", the
    Group settings link disappears, and the mobile dock unmounts entirely.
    Leaving *to* the Groups list should not feel like leaving your Group. This
    is by construction rather than a wiring fault — `/groups` sits outside
    `/g/<slug>`, and the current Group is read from the URL per ADR-0002 — so
    the fix is a presentation decision, not a change to how the Group is
    resolved.
  - **Where:** `/groups` -> `src/routes/_app/groups.tsx`;
    `src/components/app/useNavigation.ts:26` and
    `src/components/app/useCurrentGroup.ts` (both derive from
    `groupSlugOf(location.pathname)`, which returns null off a `/g/` route);
    `src/components/app/Sidebar.tsx:53-56` (the "Pick a group" fallback) and
    `:94` (the vanishing settings link);
    `src/components/app/MobileDock.tsx:23` (`if (shown.length === 0) return null`).
    ADR: `docs/adr/` — the URL-is-the-Group decision (ADR-0002) must not be
    weakened.
  - **Type:** UX
  - **Fix direction:** Keep the URL as the single source of truth for the active
    Group — do not introduce a second, stateful notion of "current Group".
    Instead let the shell remember the last `/g/<slug>` visited (in the shell,
    not in Convex) purely for *presentation* on slugless routes: keep the module
    list and the dock rendered against that Group while on `/groups`,
    `/settings` and `/account`, with the switcher continuing to show it. If that
    is judged too much for this PR, the smaller fix is to make the slugless
    sidebar state useful rather than empty — list the reviewer's Groups as
    direct links instead of the single "Pick a group to see its modules."
    sentence.
  - **Acceptance:** Navigating from a Group's Home to `/groups` and back leaves
    the sidebar and dock coherent throughout — no moment where the shell shows
    no Group and no modules. The active Group is still read from the URL on
    every `/g/<slug>` route (existing Group-gate and navigation tests stay green
    unmodified).
